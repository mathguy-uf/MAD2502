# Capstone Start Here

[← Capstone home](README.md)

The capstone is your chance to use Python and data to investigate a question your team cares about.

You are **not expected to begin as a data scientist**. This is a first Python/data-science course. A successful project can use simple methods very well.

## 1. What is a capstone project?

A capstone brings together the main skills from the course in one project:

1. ask a question;
2. find data that can help answer it;
3. use Python to inspect and analyze the data;
4. explain what the evidence supports;
5. communicate the result clearly;
6. leave enough documentation that someone else can follow your work.

That is the project. You do **not** need advanced machine learning.

## Your first goal: a minimum viable project

Before trying anything ambitious, build one complete path:

**question → data → one Python result → explanation**

For example:

- question: Which category appears most often?
- data: a CSV you can load;
- result: `value_counts()`;
- explanation: one or two sentences saying which category is most common and how many records support that conclusion.

Once that works, you can improve the question or add another analysis.

## Good beginner analyses

A project can be strong using:

- counts or percentages;
- mean or median;
- grouped summaries;
- comparisons;
- rankings;
- distributions;
- scatter plots;
- time trends;
- correlation with caveats;
- simple regression when justified;
- simulation.

The method should match the question. More complicated does not automatically mean better.

## Before you start coding

Write down these answers in plain English:

- What are we trying to learn?
- What data might help?
- What does one row or record represent?
- Which variables or columns would we need?
- What would one useful result look like?
- What would the data **not** be able to prove?

It is okay if some answers are uncertain. The next steps are designed to test them.

## A beginner-friendly way to divide team work

Do not divide the team into “coder,” “writer,” and “presenter” who never overlap.

Instead, rotate and review tasks:

- source/documentation investigation;
- loading and cleaning;
- summaries and visualizations;
- interpretation and writing.

Everyone should understand the main question, data source, analysis, and conclusion.

## Keep evidence of the process

Every work session should produce two things:

1. one small piece of progress, even if that progress is discovering what does **not** work;
2. one [project journal](05_project_journal.md) entry.

A failed attempt is useful when it changes a decision.

## Beginner checkpoint

Before moving to the next step, your team should be able to say:

> We can explain our current question in one sentence, and we know the next small thing we need to test.

If not, make the question smaller.

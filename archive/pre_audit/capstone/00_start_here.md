# Capstone Start Here

[← Capstone home](README.md)

The capstone is your chance to use Python to investigate a question you care about.

You are **not expected to begin as a data scientist**. This is an introductory course. A successful project can start with simple Python and become more sophisticated as your team learns.

## What a capstone project actually is

A capstone project has four basic ingredients:

1. **A question** you want to investigate.
2. **Data** that can help answer that question.
3. **Python work** that turns the raw data into useful evidence.
4. **An explanation** of what you found, including limitations and detours.

That is enough to begin.

## A reasonable first milestone

Your first goal is **not** to build a machine-learning model.

Your first goal is to get one complete path working:

```text
source
  ↓
Python reads the data
  ↓
you inspect the rows and columns
  ↓
you compute one useful result
  ↓
you make one labeled graph or table
  ↓
you explain what it means
```

If your team can do that, the project is moving.

## What counts as a useful first result?

Examples:

- mean or median of an important variable;
- counts by category;
- comparison of two groups;
- trend over time;
- top or bottom values;
- a scatter plot showing the relationship between two numeric variables;
- a histogram showing a distribution;
- one API request converted to a DataFrame;
- one webpage table loaded and cleaned;
- a simple regression or classification result **only if your question needs it**.

## Questions to answer before coding

Write down answers to these questions in plain English:

- What are we trying to learn?
- What does one row of our data represent?
- Where did the data come from?
- Which columns seem important?
- Which column is the outcome or quantity we care most about?
- What would a meaningful graph look like?
- What result would make us say, “That is interesting”?

If you cannot answer these yet, that is normal. The next step is to inspect the data and refine the question.

## A beginner-friendly division of work

Teams should not divide the project into “one person codes, one person writes, one person presents.” Everyone should understand the main analysis.

A better division is by tasks that still overlap:

- one person investigates sources and documentation;
- one person experiments with loading/cleaning;
- one person develops visualizations or summaries;
- everyone reviews the code and interpretation together.

Rotate tasks as the project develops.

## Keep a project journal

Every time your team works, record:

- date;
- what you tried;
- what worked;
- what failed;
- what you changed;
- new questions;
- next step.

A five-minute journal entry can save hours when writing the final report.
